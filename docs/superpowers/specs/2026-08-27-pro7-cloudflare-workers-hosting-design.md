# PRO7 Cloudflare Workers Free Hosting Design

**Date:** 2026-08-27  
**Status:** Approved in chat; awaiting written-spec review  
**Scope:** Move public production hosting from the blocked Oracle VM path to the user's Cloudflare account without changing the PRO7 frontend or Supabase data model.

## Context

Oracle Singapore rejected both Always Free shapes (`VM.Standard.A1.Flex` and `VM.Standard.E2.1.Micro`) for lack of AD-1 capacity. No Oracle instance, boot volume, or VCN exists.

The PRO7 application is an existing multi-route Vinext application. It already builds Cloudflare Worker-compatible ESM through `@cloudflare/vite-plugin`, uses live Supabase project `pficsujapinkmqsyvcfw`, and retains an existing Sites deployment described by `.openai/hosting.json`.

The user's Cloudflare account currently has:

- Workers Free as the current plan;
- no Workers or Pages projects;
- the public account subdomain `hunglt28-work.workers.dev`;
- no custom domain requirement for this release.

## Goals

1. Publish the current verified PRO7 application as a direct Cloudflare Worker on the Free plan.
2. Use the stable initial origin `https://pro7-team-manager.hunglt28-work.workers.dev`.
3. Continue using the existing live Supabase database, Auth, Storage, Edge Functions, RLS, and RPCs.
4. Preserve the current UI, responsive behavior, routes, and permission model.
5. Keep the existing `chatgpt.site` deployment intact as a fallback.
6. Prove Admin and Member flows on the public origin before declaring the hosting migration complete.

## Non-goals

- No frontend redesign or component restructuring.
- No database schema migration, seed, or production-data rewrite.
- No Cloudflare D1, R2, KV, Hyperdrive, Durable Objects, Pages project, custom domain, or paid Workers plan.
- No deletion or modification of the existing Sites deployment.
- No Oracle resource retry or paid Oracle fallback in this plan.
- No automatic upgrade when a Cloudflare Free limit is exceeded.

## Selected architecture

Deploy one Worker named `pro7-team-manager` through the pinned Vinext and Wrangler toolchain already present in the repository.

The request path is:

```text
Browser
  -> https://pro7-team-manager.hunglt28-work.workers.dev
  -> Cloudflare Worker / Vinext RSC + route handlers
  -> Supabase HTTPS APIs
  -> PostgreSQL RLS/RPC, Auth, Storage, Edge Functions
```

Static assets are served by the Worker's asset binding. Dynamic pages and API routes execute in the Worker. Supabase remains the sole application persistence and authorization authority.

The direct Worker is independent of `.openai/hosting.json`. The existing Sites plugin and project metadata remain in place so the fallback deployment is not broken. Cloudflare-specific production configuration is additive and must not change rendered UI.

## Why Workers, not Pages

Vinext has a native Cloudflare Workers deployment path using `@cloudflare/vite-plugin`. Pages Functions use Workers billing and limits but introduce a second hosting model without product benefit. A direct Worker also satisfies the user's requirement that the deployment be visible and manageable in their Cloudflare dashboard.

## Free-plan safety boundary

The deployment is authorized only while the Cloudflare account shows Workers Free as the current plan. The implementation must not press Upgrade, attach a paid product, create a payment subscription, or enable a feature marked paid.

The release gate is:

- Worker bundle gzip size is at most 3 MB;
- no more than the existing two Supabase public environment values are required;
- no paid binding or service is declared;
- Wrangler dry-run succeeds before remote deployment;
- deployment targets exactly `pro7-team-manager` in the approved account;
- the generated Worker config retains `nodejs_compat` and static assets;
- the public deployment uses `workers.dev`, not a paid/custom domain feature.

Workers Free currently allows 100,000 requests per day, 10 ms CPU time per request, 128 MB memory, 50 external subrequests per request, and a 3 MB compressed Worker. The application may occasionally exceed the 10 ms CPU allowance because it performs SSR and authentication. If Cloudflare rejects the bundle or runtime requests consistently exceed Free CPU, the plan stops with the existing Sites deployment preserved. It must not silently upgrade to Workers Paid.

## Source and deployment configuration

Use the existing pinned versions in `package-lock.json`. Do not install a floating global or latest deployment tool.

Add a small, explicit Cloudflare production contract to the existing Vite/Worker configuration:

- Worker name: `pro7-team-manager`;
- compatibility date pinned in source;
- compatibility flag: `nodejs_compat`;
- Worker entry and static assets generated by Vinext;
- no D1/R2/KV/DO/queue/AI bindings;
- account selection supplied at deployment time, not committed as a personal account ID;
- environment values supplied without printing or committing their contents.

The deployment command must build from a clean generated output, inspect the generated `dist/server/wrangler.json`, execute a Wrangler dry-run, and only then upload that exact output. The source must contain a repeatable script and contract test rather than relying on manual dashboard editing.

## Environment and secret handling

The application requires only:

- `NEXT_PUBLIC_SUPABASE_URL`;
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`.

The URL must equal the approved Supabase project URL. The publishable key must pass the repository's existing public-key validation and must never be replaced by a service-role or secret key.

The local ignored `.env.local` remains the build source. Environment values must never be printed, committed, copied into documentation, passed in a remote URL, or stored in browser-visible source control settings. If the generated Worker needs runtime bindings in addition to build-time replacement, configure the same two values as Worker secrets through authenticated Wrangler commands.

## Cloudflare authentication

Use Wrangler OAuth login for the user's already authenticated Cloudflare account. The login grant is limited to the permissions Wrangler requires to manage Workers. Do not create a broad manual API token unless OAuth is unavailable. The user must confirm the OAuth authorization in the Cloudflare browser UI when prompted.

Before deployment, `wrangler whoami` must resolve the approved account and Free plan context. No account identifier or OAuth credential is committed.

## Supabase origin changes

Only after the Worker returns a healthy public response, add the exact new origin:

`https://pro7-team-manager.hunglt28-work.workers.dev`

Supabase Auth configuration must retain localhost and the existing `chatgpt.site` redirect origin while adding the Worker callback/reset destinations.

The project-wide Edge Function `ALLOWED_ORIGINS` value must become the exact comma-separated set of approved origins. Wildcards, suffix matching, and arbitrary `workers.dev` origins are forbidden. `provision-team-member` and `change-temporary-password` remain JWT-protected and are not redeployed unless their checked-in code differs from the deployed version.

No Supabase schema, RLS policy, role, user, team, match, attendance, tactics, fund, or settings data is changed as part of hosting configuration.

## Verification

### Local and dry-run gates

- Existing unit suite passes.
- Existing production build and rendered HTML suite pass.
- Cloudflare hosting contract tests pass.
- Generated Worker name, entry, compatibility flags, bindings, and assets are exact.
- Wrangler dry-run succeeds and reports gzip size within the Free limit.
- No server bundle contains a Supabase service-role or secret key.

### Public unauthenticated checks

- HTTPS works at the exact `workers.dev` hostname.
- `/login` renders without a Worker resource error.
- `/` follows the current authentication redirect behavior.
- Static fonts, icons, CSS, and client chunks load.
- An unapproved origin fails Edge Function CORS.

### Authenticated Admin checks

- Login and logout work.
- Team landing resolves to the current `nat-fc` slug.
- Overview, Squad, Matches, Tactics, Funds, and Admin Settings load according to permissions.
- A safe reversible CRUD smoke test succeeds through the same RLS/RPC boundaries used locally.
- Admin sees Funds and the correct mobile bottom navigation count/alignment.

### Authenticated Member checks

- Member login and forced-password-change behavior remain correct.
- Funds and Admin Settings remain inaccessible.
- Notifications load and can be marked read.
- Match invitation and RSVP response are visible to the Member and reflected to Admin.
- Member self-profile updates remain self-only.

### Responsive checks

Test representative Admin and Member routes at 390 px and desktop width. There must be no horizontal overflow, clipped modal, hidden primary action, or navigation regression. This is verification only; frontend redesign is out of scope.

## Rollback and failure handling

The current Sites deployment remains the rollback target throughout the Cloudflare release.

If the Worker deployment fails before a healthy version exists, no Supabase origin setting is changed. If the Worker deploys but public/authenticated verification fails, do not route users to it and revert any new Supabase origin configuration. A failed Worker may remain undeployed or disabled without creating a paid plan; deletion requires a separate explicit destructive-action confirmation.

If the only failure is the Workers Free 10 ms CPU ceiling or 3 MB bundle ceiling, report the incompatibility and stop. Do not enable Workers Paid, Containers, or another billable service.

## Acceptance criteria

The hosting migration is complete only when:

1. Cloudflare dashboard shows one `pro7-team-manager` Worker on the Free plan.
2. The exact `workers.dev` URL serves PRO7 over HTTPS.
3. Supabase accepts only the exact approved origin set.
4. Admin and Member route/permission/RSVP smoke tests pass publicly.
5. Mobile and desktop verification show no regression.
6. No paid Cloudflare product, new Supabase schema, production seed, or frontend redesign was introduced.
7. The existing Sites deployment remains available as fallback.
